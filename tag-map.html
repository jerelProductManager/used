site_type and page_type are page-level constants, not per-event values.

Every GA4 event on this page carries site_type: "Desktop" and page_type: "productList", stamped by the analytics worker rather than by the component that fired. They are reproduced in every row below so the grid is complete, but the only rows where they vary are the Google Ads remarketing sends, which omit both. There is no dataLayer in the GTM sense — B&H pushes gtag('event', name, params) directly from a service-worker-backed analytics module.

Findings

F1 · bug

Category refinements send the string "undefined"

Clicking a link in the left-rail Categories block fires a Filters event whose filter_value and from are the literal string "undefined", and whose filter_n_value holds the human-readable name — the inverse of how every other facet populates. Sensor Size sends filter_value: "Full Frame (35mm)" / filter_n_value: "fct_sensor-size_3087"; Category sends the display name in the machine-code slot and nothing usable in the other two.

Sensor Size filter_value: "Full Frame (35mm)" filter_n_value: "fct_sensor-size_3087" from: "left refinements" Category filter_value: "undefined" filter_n_value: "Mirrorless Cameras" from: "undefined"

Any GA4 report that segments refinement usage by filter_value silently buckets all category navigation into a single "undefined" row, and from can't distinguish left-rail from top-bar for these clicks at all.

F2 · gap

The See-All facet modal is almost entirely untagged

Opening the modal fires. Clear All fires. Nothing else does — not the individual facet checkboxes inside it, not Select All, not Cancel, not Apply Selection. So a filter applied from the modal is invisible, while the same filter applied from the rail is captured. Facet-usage numbers are biased toward the rail by an unknown factor, and the modal's abandon rate can't be measured at all.

F3 · gap

"See all" doesn't say which facet was opened

Listing See All Info sends label: "left refinements" — the placement, which is already implied by the component. The facet name (Sensor Size, Brand, Still Image Resolution) is never sent, so you can see that shoppers open the modal without seeing which attributes drive them there. Since Filter Labels already proves the section name is available at this layer, this is a one-line fix.

F4 · gap

Sort fires twice, once with an empty label

Opening the dropdown emits Sort By with label: ""; choosing an option emits it again with the enum. Unless reports filter on a non-empty label, sort engagement is inflated roughly 2× and the empty-label rows read as a broken value rather than an open-menu signal. Separately, the label is the raw enum PRICE_LOW_TO_HIGH rather than the displayed text, so anyone reading the report has to translate.

F5 · gap

Tile-level interactions carry no item identifier

Show More and Add to Compare both fire with no label, no label_value, and no items[]. You get a count of how often shoppers expand specs or compare, but never which products — which is exactly the cut needed to tell whether spec-hunger clusters on particular categories or price bands. The worker's schema already supports items: [{ item_id }] on this event family (select_item and Other Buying Options both use it), so the plumbing exists.

F6 · note

The Used entry point is the best-tagged thing on the page

Other Buying Options is the only component here that fills all of component, label and label_value — label: "Used" identifies the buying-option type and label_value: "1910936-REG" the SKU. That means used-inventory click-through from new-product listings is measurable per SKU today, without new tagging. Paired with the hero select_promotion pointing at /a/trade-in/64435, both listing-page routes into the Used and trade-in funnel are already instrumented — the entry-point breakdown that the trade-in measurement framework flags as "needs tagging" is, for this surface, already available.

F7 · note

Two things worth knowing about the schema

There is no GTM dataLayer to inspect — window.dataLayer is empty until the analytics module boots and then receives gtag() calls directly. Universal Analytics (analytics.js) is still loading on this page alongside GA4. And despite the /c/buy/ URL, the page identifies as page_type: productList and emits listing_page_clicks; the separate category_page_clicks event in the taxonomy belongs to a different template, so don't look for this page's traffic there.
